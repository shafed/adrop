# adrop — действующие решения

Сводка решений, которые действуют сейчас, и почему. Поведение — `SPEC.md`,
очередь — `PLAN.md`, состояние — `STATE.json`, результат ворот — заметки
`refs/notes/gate`. Файл **правится, а не дописывается**: новое решение
вписывается в свой раздел, отменённое убирается, в том же коммите, что и
работа. Прежний журнал — `HANDOFF.md` в истории git.

## Протокол

- Кадр: 4 байта big-endian — длина JSON-заголовка, JSON, затем ровно
  `length` байт полезной нагрузки. Ключи в snake_case (`file_index`,
  `bytes_done`); нулевые значения опускаются (`omitempty`), Kotlin
  кодирует с `encodeDefaults = false, explicitNulls = false`.
- Fingerprint — SHA-256 от DER сертификата, 64 символа нижним регистром hex,
  без двоеточий.

## Идентичность и адреса

- Идентичность ПК — ECDSA P-256: Android BoringSSL не объявляет ed25519 среди
  алгоритмов подписи сертификата. Смена идентичности ломает все QR и пары.
- Адрес пира: порт из его Hello главный; пустой/`0.0.0.0`/`::` хост
  заменяется адресом источника соединения; без порта — `DefaultPort`
  (`resolvePeerAddr`). Адрес чинится при каждом входящем соединении.

## Ядро и Flutter (шаг 1 PLAN.md, прототип)

- Ядро — `core/`: тот же `daemon.Daemon`, только без слушателя и IPC;
  наружу — `Start`, `Fingerprint`, `Pair`, `Peers`, `Hello`. Своей реализации
  протокола у ядра нет.
- Android: `gomobile bind` → `com.adrop.proto.core`; вызовы из Flutter через
  канал `adrop/core` в `MainActivity.kt` на отдельном потоке. Linux:
  `core/cshared` (`c-shared`), ответы — JSON `{ok,result,error}`, вызовы из
  Dart в `Isolate.run`.
- Прототип `app/` ставится как `com.adrop.proto` рядом с `com.adrop`, у него
  своя идентичность (на Linux — `$XDG_DATA_HOME/adrop-proto`).
- Размер `.aar`: 5,9 МБ только arm64, 12 МБ arm64+amd64, 25 МБ все четыре ABI.
  Поэтому по умолчанию `scripts/build-core.sh android` собирает только arm64.
- Проверено 2026-10-25: Linux-окно на Xvfb, эмулятор и SM-S721B (arm64,
  release-APK 24 МБ) по Wi-Fi до демона ПК — сопряжение и Hello проходят.
- `Pair` в ядре считается успешным, только если пир ответил на Hello: иначе
  пир не закрепил это устройство, а каждый следующий Hello получает
  `tls: bad certificate`. Так и было на телефоне, когда на ПК не было открыто
  окно `adrop pair show`.
- Ввод через `adb shell input text` ненадёжен: строка обрезается, а
  клавиатура Samsung вставляет пробел после `?`. URI на телефон передаётся
  через `adrop clip`.
- `golang.org/x/mobile` требует `go 1.26` в `go.mod`.
- Android-сборки — через стенд `../pulsar/scripts/android/emu.sh flutter`:
  Gradle-кэши и `build/` там на `/mnt/hdd`, сборка с `~/Android/Sdk` и
  `~/.gradle` занимает на корневом SSD около 6 ГБ.

## Сопряжение нажатием (шаг 2)

- Тот же порт, ALPN `adrop-pair/1`: TLS без пиннинга только для клиента,
  предложившего этот ALPN, и только при `ADROP_TAP_PAIR=1` (по умолчанию
  выключено). Обычный pinned-путь и старые клиенты не меняются.
- Код — 6 цифр из SHA-256(`adrop-pair-code` + отсортированная пара
  fingerprint). Обе стороны шлют `pair_request` (имя, адрес, ключ RNS), затем
  `pair_confirm{ok}`; устройство сохраняется, только когда оба ответа «да».
  MITM даёт разные коды (тест `TestTapPairingManInTheMiddleChangesCodes`).
- Остаток двух генералов: если связь рвётся между последними `pair_confirm`,
  одна сторона может сохранить пару, а другая нет; лечится повторным
  сопряжением.
- «Рядом» — все записи `_adrop._tcp` из avahi (`adrop nearby`), включая
  несопряжённые; на Android их передаёт ядру `AddNearby` (NsdManager).

## Связь вне LAN (шаг 3)

- Reticulum — upstream `git.quad4.io/Networks/Reticulum-Go` v0.9.5 (Apache-2.0),
  включается `ADROP_RNS=1`. Свой код — `internal/rns`. Identity —
  `<config>/rns/reticulum.id`, транспорт держит свою там же (иначе пишет в
  `~/.reticulum`).
- Обходы upstream: `identity.NewIdentity`, а не `New` (у `New` пустой хеш —
  соль ключей, пакеты не расшифровываются); свой TCP-интерфейс к хабу
  (`hubconn.go`), потому что у `TCPClientInterface` гонка данных в
  переподключении и он сам долбит мёртвый хаб.
- Хаб-на-Go не годится для тестов: его TCP-сервер — один интерфейс на всех
  клиентов, announce между ними не пересылается и идёт без transport ID.
  Тесты берут настоящий `rnsd` (`ADROP_RNSD` или `PATH`, `pip install rns`),
  без него пропускаются.
- Сигнальное сообщение: публичный ключ (64) + время (8) + тело + подпись (64),
  шифруется Reticulum на identity получателя. Тело ≤ 247 байт
  (`EncryptedMDU` 383 − 136); длиннее пакет теряется по дороге, поэтому
  `Send` его не принимает. Старше 5 минут и от несопряжённых — отбрасываются.
- Ключ RNS приезжает в QR (компактная версия 3, URI 670 байт, QR версии 21),
  в `pair_request` и в Hello (поле `rns`) — уже сопряжённые устройства
  получают его при первом соединении в LAN.
- Хабы: встроенный список (замер 2026-10-25 из домашней сети) + каталог
  `directory.rns.recipes/api/directory/submitted` (кэш
  `<config>/rns/catalog.json`). Держится 3; хаб плохой, если соединение не
  держится 20 с или 90 с нет данных (рабочий хаб всегда шлёт поток announce);
  плохой не берётся 30 мин. Кандидаты берутся по порядку, а не случайно:
  иначе два устройства садились на разные хабы и путь между ними не находился.
- Из этой сети 2026-10-25: testnet Amsterdam/Dublin недоступны,
  BetweenTheBorders принимает и закрывает; 61 из 62 хабов каталога работают.
  Ping между двумя демонами через публичные хабы — около 0,5 с.
- Прямой канал (`internal/direct`): pion/ice (host + srflx, STUN Google,
  Cloudflare, Nextcloud) → QUIC (quic-go) поверх ICE → pinned TLS 1.3, ALPN
  `adrop/1`, один поток — обычная сессия. Кандидаты — сигналы `ice-offer`,
  `ice-answer`, `ice-cand`. Отправка пробует LAN (5 с, если есть запасной
  путь), mDNS, затем прямой канал, затем FCM.
- Без прямого канала: буфер обмена до 4 КиБ — через хабы кусками по 138 байт
  с `clip-ack`; файлы и длинный буфер — в очередь `<config>/queue.json` с
  причиной (`adrop queue`), повтор каждые 2 мин и при любом сигнале от
  устройства. В очередь попадает только «не достучались»; отказ получателя
  из очереди убирается.

## Не проверено вживую

- Строка `hello from <имя> (<fingerprint>)` в журнале установленного демона:
  он собран до этой правки и пишет `receive from <имя>: EOF`. Её проверили
  тестом и на отдельном демоне, собранном из HEAD.
- Работа Go-горутин, когда процесс Android уходит в фон.
- Прототип в Hello объявляет адрес `<IP>:53127` — на телефоне это порт старого
  приложения, поэтому отправка с ПК на устройство «… proto» не дойдёт.
  Прототипу это не нужно; устройство можно убрать через `adrop revoke`.
- Шаг 2 на устройствах: ПК ↔ ПК проверено двумя демонами на одной машине,
  телефон — нет.
- Шаг 3 в разных сетях: всё проверено на одной машине (два демона через
  публичные хабы, прямой канал с host-кандидатами); NAT, мобильный интернет и
  symmetric NAT не проверялись.
