# adrop — действующие решения

Сводка решений, которые действуют сейчас, и почему. Поведение — `SPEC.md`,
очередь — `PLAN.md`, состояние — `STATE.json`, результат ворот — заметки
`refs/notes/gate`. Файл **правится, а не дописывается**: новое решение
вписывается в свой раздел, отменённое убирается, в том же коммите, что и
работа. Прежний журнал — `HANDOFF.md` в истории git.

## Протокол

- Кадр: 4 байта big-endian — длина JSON-заголовка, JSON, затем ровно
  `length` байт полезной нагрузки. Ключи в snake_case (`file_index`,
  `bytes_done`); нулевые значения опускаются (`omitempty`), Kotlin
  кодирует с `encodeDefaults = false, explicitNulls = false`.
- Fingerprint — SHA-256 от DER сертификата, 64 символа нижним регистром hex,
  без двоеточий.

## Идентичность и адреса

- Идентичность ПК — ECDSA P-256: Android BoringSSL не объявляет ed25519 среди
  алгоритмов подписи сертификата. Смена идентичности ломает все QR и пары.
- Адрес пира: порт из его Hello главный, хост — адрес источника соединения
  (телефон под VPN объявляет адрес `tun0`, а приходит с адреса в LAN); хост из
  Hello — только при источнике на loopback; без порта — `DefaultPort`
  (`resolvePeerAddr`). Адрес чинится при каждом входящем соединении.

## Ядро и приложение (шаги 1, 4, 5)

- Протокол один — Go. Телефон: Go-ядро (`core/`, gomobile, пакет
  `com.adrop.core`) внутри foreground-сервиса `AdropService`; Flutter зовёт
  его через `MainActivity` (канал `adrop/core`, события — `adrop/events`).
  ПК: окно `adrop-gui` — клиент демона по Unix-сокету, как CLI; `adrop` без
  аргументов запускает его. Старое окно на Fyne, Kotlin-приложение со своим
  протоколом и прототипная FFI-обёртка удалены после сверки действий.
- Телефон делает сам: NsdManager (анонс `_adrop._tcp` с TXT `fp`, поиск →
  `AddNearby`), буфер обмена, уведомления, перенос принятого в MediaStore
  `Download/` (со структурой папок), «Поделиться», выбор папки (SAF-дерево
  копируется в кэш), автозапуск после загрузки.
- Приложение — `com.adrop`, minSdk 29 (MediaStore Downloads без широких прав
  на хранилище). Старое приложение с тем же id подписано другим ключом —
  перед установкой его нужно удалить.
- Настройки телефона (по умолчанию выключены): приём при закрытом приложении
  (постоянный сервис, тип `specialUse`: у `dataSync` на Android 15 лимит
  6 ч в сутки), сопряжение по коду, Reticulum.
- Очередь исходящих на телефоне работает и без Reticulum
  (`QueueUnreachable`): отправка на недоступный ПК ждёт и уходит, когда
  NsdManager снова его видит. На ПК без Reticulum отправка по-прежнему
  сразу сообщает ошибку.
- LAN-адрес телефон набирает через интерфейс, чья подсеть содержит этот адрес
  (`SO_BINDTODEVICE`, `transport.BindLANDials`, только ядро телефона): при слабом
  Wi-Fi Android делает основной мобильную сеть, Wi-Fi остаётся подключён, и сокет
  приложения без привязки уходит в `rmnet` (2026-10-31: отправка висела почти
  минуту, с привязкой — 149 мс при том же маршруте).
- VPN на телефоне: приложение, которое он держит, принимает входящие только с
  `tun` (`IIF_MATCH` в `dumpsys connectivity trafficcontroller`), и ПК не
  подключается по LAN — только в обход через ICE (11 с вместо 196 мс). Поэтому
  `com.adrop` исключён из Pulsar («Bypass VPN»), как Syncthing; это настройка
  телефона, в коде её нет. Хабы и STUN при этом идут мимо VPN.
- FCM: новое приложение токен не шлёт; `adrop-relay` на ПК остаётся до
  решения шага 4 (замер батареи).
- `.aar`: 20 МБ на arm64+amd64. `gomobile bind` нужен
  `-ldflags=-checklinkname=0` (pion/ice → `wlynxg/anet`, обход скрытых
  сетевых интерфейсов Android 11+).
- Android-сборки — через стенд `../pulsar/scripts/android/emu.sh flutter`:
  Gradle-кэши и `build/` там на `/mnt/hdd`, сборка с `~/Android/Sdk` и
  `~/.gradle` занимает на корневом SSD около 6 ГБ. `adb shell input text`
  ненадёжен (обрезает строки, клавиатура Samsung вставляет пробел после `?`).

## Сопряжение нажатием (шаг 2)

- Тот же порт, ALPN `adrop-pair/1`: TLS без пиннинга только для клиента,
  предложившего этот ALPN, и только при `ADROP_TAP_PAIR=1` (по умолчанию
  выключено). Обычный pinned-путь и старые клиенты не меняются.
- Код — 6 цифр из SHA-256(`adrop-pair-code` + отсортированная пара
  fingerprint). Обе стороны шлют `pair_request` (имя, адрес, ключ RNS), затем
  `pair_confirm{ok}`; устройство сохраняется, только когда оба ответа «да».
  MITM даёт разные коды (тест `TestTapPairingManInTheMiddleChangesCodes`).
- Остаток двух генералов: если связь рвётся между последними `pair_confirm`,
  одна сторона может сохранить пару, а другая нет; лечится повторным
  сопряжением.
- «Рядом» — все записи `_adrop._tcp` из avahi (`adrop nearby`), включая
  несопряжённые; на Android их передаёт ядру `AddNearby` (NsdManager).

## Связь вне LAN (шаг 3)

- Reticulum — upstream `git.quad4.io/Networks/Reticulum-Go` v0.9.5 (Apache-2.0),
  включается `ADROP_RNS=1`. Свой код — `internal/rns`. Identity —
  `<config>/rns/reticulum.id`, транспорт держит свою там же (иначе пишет в
  `~/.reticulum`).
- Обходы upstream: `identity.NewIdentity`, а не `New` (у `New` пустой хеш —
  соль ключей, пакеты не расшифровываются); свой TCP-интерфейс к хабу
  (`hubconn.go`), потому что у `TCPClientInterface` гонка данных в
  переподключении и он сам долбит мёртвый хаб.
- Хаб-на-Go не годится для тестов: его TCP-сервер — один интерфейс на всех
  клиентов, announce между ними не пересылается и идёт без transport ID.
  Тесты берут настоящий `rnsd` (`ADROP_RNSD` или `PATH`, `pip install rns`),
  без него пропускаются.
- Сигнальное сообщение: публичный ключ (64) + время (8) + тело + подпись (64),
  шифруется Reticulum на identity получателя. Тело ≤ 247 байт
  (`EncryptedMDU` 383 − 136); длиннее пакет теряется по дороге, поэтому
  `Send` его не принимает. Старше 5 минут и от несопряжённых — отбрасываются.
- Ключ RNS приезжает в QR (компактная версия 3, URI 670 байт, QR версии 21),
  в `pair_request` и в Hello (поле `rns`) — уже сопряжённые устройства
  получают его при первом соединении в LAN.
- Хабы: встроенный список (замер 2026-10-25 из домашней сети) + каталог
  `directory.rns.recipes/api/directory/submitted` (кэш
  `<config>/rns/catalog.json`). Держится 3; хаб плохой, если соединение не
  держится 20 с или 90 с нет данных (рабочий хаб всегда шлёт поток announce);
  плохой не берётся 30 мин. Кандидаты берутся по порядку, а не случайно:
  иначе два устройства садились на разные хабы и путь между ними не находился.
- Announce — при подключении хаба и каждые 2 мин. Reticulum-Go v0.9.5 забывает
  путь через `PathRequestTTL` (5 мин) после последнего announce, а запрос пути
  его не возвращает: хаб отвечает тем же закэшированным announce, и транспорт
  час (`SeenAnnounceTTL`) отбрасывает его как дубликат. При прежних 10 мин
  устройство было недостижимо с 5-й по 10-ю минуту (2026-10-25: `adrop ping`
  в 13:29 — `no path to the peer`, в 13:32 — `pong`). `pulsar-direct` чинит
  это патчем транспорта (дубликат принимается, когда пути нет); здесь upstream
  не патчится.
- Из этой сети 2026-10-25: testnet Amsterdam/Dublin недоступны,
  BetweenTheBorders принимает и закрывает; 61 из 62 хабов каталога работают.
  Ping между двумя демонами через публичные хабы — около 0,5 с.
- Прямой канал (`internal/direct`): pion/ice (host + srflx, STUN Google,
  Cloudflare, Nextcloud) → QUIC (quic-go) поверх ICE → pinned TLS 1.3, ALPN
  `adrop/1`, один поток — обычная сессия. Кандидаты — сигналы `ice-offer`,
  `ice-answer`, `ice-cand`. Отправка пробует LAN (5 с, если есть запасной
  путь), mDNS, затем прямой канал, затем FCM.
- Без прямого канала: буфер обмена до 4 КиБ — через хабы кусками по 138 байт
  с `clip-ack`; файлы и длинный буфер — в очередь `<config>/queue.json` с
  причиной (`adrop queue`), повтор каждые 2 мин и при любом сигнале от
  устройства. В очередь попадает только «не достучались»; отказ получателя
  из очереди убирается.

## Windows (шаг 6)

- `make windows` → `dist/windows/adrop.exe` (CLI) и `adrop-daemon.exe`
  (без окна консоли, журнал — `%AppData%\adrop\daemon.log`). Конфиг —
  `%AppData%\adrop`. Окно — `flutter build windows` в `app/` на Windows
  (`adrop-gui.exe`); голый `adrop` его запускает.
- Буфер обмена — PowerShell `Get-Clipboard`/`Set-Clipboard`, только текст;
  уведомления — WinRT-тост через PowerShell под app id PowerShell;
  автозапуск — `adrop autostart on|off`, ключ `HKCU\…\Run`.
- mDNS без avahi — `grandcat/zeroconf` (чистый Go); на Linux остаётся
  avahi, zeroconf собирается тегом `zeroconf` для теста.
- IPC: Dart на Windows не умеет Unix-сокеты, поэтому демон слушает
  `127.0.0.1:<порт>` и пишет адрес и случайный токен в
  `%AppData%\adrop\ipc.json` (0600); первой строкой клиент шлёт токен, без
  него соединение закрывается. На Linux — прежний сокет. Логика проверяется
  на Linux тегом `ipctcp`.
- Проверено под wine (отдельный префикс): демон, IPC с токеном, `status`,
  сопряжение по коду с Linux-демоном, файлы в обе стороны, zeroconf видит
  Linux-демон и наоборот. Не проверено: буфер обмена, уведомления,
  автозапуск, окно Flutter под Windows (собирается только на Windows),
  настоящий Windows.

## Не проверено вживую

- Шаги 2–5 на реальных устройствах. Проверено: два демона на одной машине
  (сопряжение по коду, отправка, Reticulum через публичные хабы, прямой
  канал с host-кандидатами, очередь), окно на Xvfb (сопряжение по коду,
  Ctrl+V, текст, приём, QR, устройства), эмулятор Android против демона на
  хосте (NsdManager, сопряжение по коду, текст, файл в MediaStore,
  «Поделиться» текстом, папка через SAF).
- Не проверялось вообще: перетаскивание файлов в окно, выбор файлов и
  снимок камерой на телефоне, сканирование QR камерой, приём при закрытом
  приложении и расход батареи (шаг 4), NAT/мобильный интернет/symmetric NAT
  (шаг 3), два телефона.
