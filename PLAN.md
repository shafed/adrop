# План: от текущего adrop к целевому

Целевое состояние описано в [`SPEC.md`](SPEC.md). Здесь — порядок работ и то,
чем каждый шаг проверяется. Шаг считается сделанным, когда его проверка
пройдена на реальных устройствах, а не когда написан код.

Порядок выбран так, чтобы ничего не писать дважды: сначала проверяется, что
Go-ядро встраивается во Flutter, и только потом поверх него делаются новые
функции. Иначе экран сопряжения пришлось бы писать на Kotlin и на Fyne, а
потом выбросить оба.

---

## Шаг 1. Прототип: Go-ядро внутри Flutter

**Цель:** убедиться, что схема «Go-ядро + Flutter» работает на обеих
платформах, до того как в неё вкладываться.

- Вынести из `internal/daemon` минимальный API ядра: запустить, отдать
  identity, подключиться к пиру, провести `Hello`.
- Android: собрать ядро через `gomobile bind` в `.aar`, вызвать из Flutter
  через platform channel.
- Linux: собрать ядро как `c-shared`, вызвать из Flutter через `dart:ffi`.
- Минимальная Flutter-оболочка: одна кнопка «Hello», вывод результата.

**Проверка:** с телефона и с Linux-окна Flutter проходит `Hello` с
работающим демоном на ПК; демон пишет в журнал fingerprint и имя пира.

**Риски:** размер `.aar`; работа Go-горутин при уходе Android-процесса в фон;
сборка `c-shared` вместе с GUI-зависимостями. Если схема не работает — решение
про Flutter пересматривается здесь, до остальных шагов.

---

## Шаг 2. Поиск в LAN и сопряжение по нажатию

**Цель:** как в LocalSend — видны все устройства рядом, сопряжение нажатием.

- mDNS: показывать не только сопряжённые устройства, а все с `_adrop._tcp`;
  сопряжённые помечать.
- Новая сессия сопряжения: TLS без проверки fingerprint → обмен
  сертификатами → 6-значный код из пары fingerprint → подтверждение на обоих
  устройствах → сохранение.
- QR остаётся.
- Пока без Reticulum identity: её добавление в payload сопряжения — шаг 3.

**Проверка:** на реальных устройствах в одной Wi-Fi ПК ↔ ПК, ПК ↔ телефон,
телефон ↔ телефон: устройство появляется в списке, коды на двух экранах
совпадают, после подтверждения проходит передача файла. Отказ на одной стороне
— сопряжения нет ни на одной.

**Тест безопасности:** подмена соединения (MITM в тесте) даёт разные коды.

## Шаг 3. Связь вне LAN

**Цель:** сопряжённые устройства обмениваются данными из разных сетей без
своего сервера.

Подшаги, каждый проверяется отдельно:

1. **Reticulum.** Подключить upstream Reticulum-Go; у устройства появляется
   Reticulum identity; она добавляется в QR и в сопряжение по нажатию;
   хранится в `devices.json`. Демон держит соединение с несколькими хабами.
   **Проверка:** два ПК в разных сетях обмениваются подписанным сигнальным
   сообщением через хабы.
2. **Замер и замена хабов.** Хаб считается рабочим, только если держит
   соединение и доставляет данные; плохие заменяются из встроенного списка и
   каталога. **Проверка:** хаб, закрывающий соединение, вытесняется сам;
   журнал показывает замену.
3. **Прямой канал.** ICE-кандидаты через Reticulum, публичные STUN, QUIC;
   внутри QUIC — тот же pinned TLS и текущий формат сообщений.
   **Проверка:** файл передаётся между ПК дома и устройством на мобильном
   интернете (телефон в режиме модема для ноутбука или сам телефон).
4. **Без прямого канала.** Буфер и мелкие данные — через хабы; файлы ждут в
   очереди с понятной причиной в интерфейсе и уходят, когда канал поднялся.
   **Проверка:** два телефона на мобильном интернете — буфер доходит, файл
   ждёт; один переходит на Wi-Fi — файл уходит.

**Риски:** хабы недоступны из отдельных сетей без VPN (DPI); symmetric NAT у
обеих сторон; размер QR после добавления identity.

## Шаг 4. Телефон принимает при закрытом приложении

**Цель:** телефон принимает в LAN и вне её, когда приложение закрыто.

- Постоянный foreground-сервис: приём в LAN + соединение с хабами.
- **Сначала замер:** телефон с сервисом и одним хабом лежит ночь;
  расход смотрится в `dumpsys batterystats`. Сравнение — та же ночь без
  сервиса.
- Если расход заметный — запасной путь: FCM-пробуждение (для телефон ↔
  телефон нужна облачная функция Firebase; решается отдельно).

**Проверка:** приложение закрыто, экран выключен, через час с другого
устройства приходит файл (в LAN и вне её).

## Шаг 5. Flutter UI на Linux и Android

**Цель:** один интерфейс вместо Fyne и Compose.

- Экраны: список устройств («Рядом» и «Мои»), отправка, приём и его история,
  сопряжение (нажатие и QR), управление устройствами.
- ПК: окно — клиент демона через IPC, как сейчас; CLI и демон без изменений.
- Android: на Kotlin остаются foreground-сервис, MediaStore, камера, интенты
  «Поделиться»; всё остальное — ядро и Flutter.
- После переключения удалить дублирующий протокол на Kotlin и копии
  `Proto.kt` в `android/jvm-tests*`, окно на Fyne (`cmd/adrop/gui*.go`) и
  его зависимости, цели сборки с тегом `gui` в `Makefile`.

**Проверка:** сценарии из шагов 2–4 проходят через новый UI на обеих
платформах; скриншоты с реальных устройств. Перед удалением старого UI —
сверка: каждое действие и сочетание клавиш старого окна есть в новом.

## Шаг 6. Windows

- Сборка ядра и Flutter под Windows.
- Буфер обмена, уведомления, автозапуск демона — свои реализации.
- mDNS на Windows без avahi.

**Проверка:** Windows ↔ Linux и Windows ↔ телефон в LAN и вне её.

---

## Правила для всех шагов

- Новая функция коммитится отдельно от её включения по умолчанию; включается
  после того, как один раз отработала на реальных устройствах.
- Изменения протокола совместимы со старыми версиями или явно отказывают с
  понятной ошибкой (как сделано для папок через `folders: true`).
- Код `AIDevance/pulsar-direct` в adrop не переносится; используются только
  upstream-библиотеки.
